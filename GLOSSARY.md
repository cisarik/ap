# Glossary

## Analytic Programming

A coordination protocol for software work based on intent clarification,
evidence inspection, bounded tasks, validation, public verification, and
deliberate session rotation.

## AP Source Repository

The canonical repository `https://github.com/cisarik/ap` that owns the
universal AP protocol, handbooks, prompt contracts, artifact lifecycle rules,
integration tooling, and ADRs.

## Consuming Project

A Git project that integrates AP, normally by pinning the AP repository as the
`.ap/` submodule.

## Gitlink

The special Git tree entry by which a superproject records the exact commit of
a submodule. The gitlink is the consuming project's AP pin.

## Managed AP Block

The marked block in a consuming project's root `AGENTS.md` generated by
`./.ap/ap init`. It points participants to the pinned AP files without copying
the protocol text.

## COOPERATOR

Persistent protocol role: the human project owner with strategic authority and
approval responsibility for important alternatives and irreversible actions.

## ORCHESTRATOR

Persistent protocol role: the coordination layer that shapes bounded tasks,
evaluates Worker reports, verifies evidence, and manages continuation,
diagnostics, rotation, or closure.

## Orchestrator Instance

One concrete initialized entity temporarily assigned to the ORCHESTRATOR role.

## Orchestrator Session

The bounded lifecycle and context of one Orchestrator instance.

## WORKER

Persistent protocol role: bounded execution of one authoritative task with
inspection-before-change, validation, and honest reporting.

## Worker Instance

One concrete initialized entity temporarily assigned to the WORKER role for a
session.

## Worker Session

The bounded lifecycle and context of one Worker instance.

## Worker Implementation

The concrete system fulfilling the WORKER role in a session. It may be an
IDE-integrated agent, command-line agent, local or remote coding agent,
multi-agent system exposed through one accountable endpoint, or another
capable executor accepted by the project.

## Capability Profile

Functional description of what a Worker implementation can do in the current
session: repository access, filesystem writes, shell, Git, tests, network,
browser automation, multimodal inspection, context telemetry, or delegation.

## Task Authority

Permission to perform a specific bounded task, granted only by the current
authoritative Orchestrator prompt.

## Source of Truth

Repository files, tests, Git history, public commits, ADRs, specifications, and
other verifiable artifacts that outweigh memory and unstructured reports.

## Evidence

Output or repository state used to verify a claim: files, diffs, tests, command
output, logs, screenshots, or public commits.

## Assumption

A statement treated as true without independent verification. Important
assumptions must be identified and verified before high-risk action.

## Acceptance Criteria

Concrete conditions that define task completion.

## Fresh-Slice Implementation

A proportional lifecycle where one fresh Worker instance receives one
substantial coherent implementation slice, validates it, and reports evidence.

## Diagnostic Closeout

A bounded second prompt about the same implemented slice, normally read-only,
used to examine requirement coverage, negative guarantees, failure behavior,
security boundaries, documentation truth, test gaps, and Git integrity.

## Independent Fresh Audit

A sequential assignment of a separate fresh Worker instance to verify an
already implemented slice. It is not parallel execution.

## Restoration Prompt

A self-contained Orchestrator rotation prompt that restores context for a fresh
Orchestrator instance without granting repository mutation authority.

## Repository Handoff

An exceptional operational lifecycle artifact created only when material state
cannot be safely reconstructed from durable repository evidence and the next
task. It is context, not task authority.

## Context Pressure

Degradation of session quality from context limits, rate limits, duration, or
lost constraints. It belongs to concrete sessions, not persistent roles.

## Compact Communication

A mode that keeps prompts and reports concise by referencing authoritative
repository files while preserving explicit task-specific authority, boundaries,
validation, and report format.

## Numbered Cooperator Acceptance Feedback

A checklist of observable outcomes prepared by the Orchestrator for
user-visible work. The Cooperator responds with `PASS`, `FAIL`, `NOT TESTED`,
or status plus `+` commentary.

## Normative Terms

| Term | Meaning |
|---|---|
| MUST | Required |
| MUST NOT | Forbidden |
| SHOULD | Recommended |
| SHOULD NOT | Discouraged |
| MAY | Optional |
